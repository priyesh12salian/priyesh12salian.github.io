Five governance mistakes that take down a SuiteScript

A script that works on ten records and dies on a thousand is almost never a logic bug. It is governance: NetSuite stops the script when it spends its usage units. These five patterns cause most of the failures I get called in to fix.

Why scripts die quietly

Every SuiteScript entry point gets a budget of usage units. A User Event script gets 1,000. A Scheduled script gets 10,000. Each API call spends some of that budget: loading a transaction costs 10 units, saving one costs 20, running a search page costs 10. When the budget is gone NetSuite throws SSS_USAGE_LIMIT_EXCEEDED and the script stops wherever it was.

The dangerous part is that the budget is spent per execution, not per record in the test. A script tested on a sandbox with ten records looks fine. The same script on the first real month-end, with twelve hundred records, fails at record 48 and leaves the rest untouched. The error lands in the execution log, which nobody opens until a user asks why half the bills were never updated.

Mistake 1: a search inside a loop

The pattern looks harmless: for each line on a sales order, run a search to find the item's open purchase orders. One search per line, 10 units each, 100 lines, and the User Event has spent its entire budget before it saves anything.

The fix is one search before the loop. Collect every item id from the lines, run a single search with an anyof filter, and put the results in a map keyed by item. The loop then reads from memory and costs nothing. This is the single change that rescues the most scripts.

Mistake 2: loading a record to read one field

record.load on a transaction costs 10 units and pulls every sublist with it. If the script only needs the customer's terms or the vendor's currency, that is 10 units and a noticeable delay for one value.

The fix is search.lookupFields, which returns the fields you name for 1 unit, or a SuiteQL query that joins what you need in a single call. The same applies on the write side: record.submitFields changes body fields for half the cost of a load and save, and without the risk of sourcing rewriting fields you never touched.

Mistake 3: batch work in a User Event

A User Event fires when one record is saved, and that is the only record it should be busy with. I still find afterSubmit scripts that walk every open invoice for the customer, or every work order on the BOM, because that was the easiest place to put the logic.

The fix is to split the trigger from the work. The User Event writes a flag or a custom record and returns in a few units. A Map/Reduce picks up the flagged records on a schedule, or is started immediately with task.create. Each key in a Map/Reduce gets its own 1,000 units in map and 5,000 in reduce, so the volume stops mattering.

Mistake 4: a Scheduled script that never looks at the clock

Ten thousand units sounds like a lot until the loop does a load and a save per record. At 30 units a record the script stops at around 330 records, and a Scheduled script does not resume where it left off.

The fix has two parts. Check runtime.getCurrentScript().getRemainingUsage() inside the loop and, when it drops under a safe margin, save your position and resubmit the script with task.create so the next run continues. Better still, move the per-record work into a Map/Reduce, where the framework handles the paging, the retries and the yield for you.

Mistake 5: running the search yourself in getInputData

In a Map/Reduce, getInputData is allowed to return a search object. Scripts that instead run the search, page through it, and return an array pay for every page out of the stage's budget, and hold the entire result set in memory while they do it.

The fix is to return the search.create or query.create object itself. NetSuite pages through it on your behalf, charges nothing to your usage, and hands each row to map one at a time.

How I check before deploying

Three habits catch nearly all of this before it reaches production.

  • Count the units on paper first. Units per record times records per run, against the limit for the script type. The governance calculator on this site does the arithmetic and tells you when to move the work to a Map/Reduce.
  • Log remaining usage at the end of a sandbox run with a realistic volume, not ten records. If the number is under a third of the budget, the script will fail on a busy day.
  • Make every batch script restartable. A record that has been processed must be safe to process again. Then a usage failure costs a re-run, not a cleanup.

None of this is clever. It is the difference between a script that passed UAT and one that survives month-end.
