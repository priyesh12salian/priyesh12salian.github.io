What a manufacturing rollout taught me about NetSuite work orders

A discrete manufacturer ran production in spreadsheets and reconciled costs by hand every month end. Moving that into NetSuite work orders taught me where the module is unforgiving, and which decisions made early decide whether costing ever becomes trustworthy.

Start with the BOM, not the work order

The first instinct is to configure work orders, because that is what the shop floor sees. The work order is the least important object in the chain. It only consumes what the bill of materials and the routing say it should, so every mistake upstream appears on every build downstream.

We spent the first two weeks on assembly items and multi-level BOMs: which components were real, which were phantom sub-assemblies, and which quantities had been padded over the years to hide scrap. Loading the spreadsheets as they were would have been faster and would have made every cost report wrong from day one.

Routings decide what you can measure

A routing is a list of operations on work centres with setup and run times. It is tempting to create one operation called "Build" and move on. Then the first question from finance is why labour cost per unit is the same on a two-minute part and a two-hour assembly, and there is no answer, because the routing never separated them.

The rule we settled on: one operation per point where somebody could reasonably be asked "is this step done yet?". Fewer operations than that and you lose visibility; more and operators stop recording them. Work centres map to physical areas, not to people, so the routing survives a staffing change.

Material issue: when, not whether

NetSuite can issue components to a work order when it is released, or as each operation completes. Both are correct. Choosing the wrong one for the shop floor is what breaks inventory accuracy.

For this client components were kitted before a build started, so issuing on release matched what physically happened. A SuiteScript on the work order release posts the issue and leaves nothing for the operator to remember. Where materials are pulled during the build, backflushing on completion is the honest choice. The point is that the system should record the moment stock actually left the shelf, because that is the moment finance will try to reconcile later.

Completions are the data finance wants

Operators record completions: how many units finished an operation, how many were scrapped. This is the only place actual quantities and actual time enter the system, so it has to be fast. A screen that takes a minute will be filled in at the end of the shift from memory, and the numbers will be smooth and wrong.

We cut the completion form down to the fields that change, defaulted everything else from the routing, and validated server-side so a bad entry is rejected on the spot rather than discovered at month end. Completion tracking in SuiteScript then posts the WIP movement without anyone pressing a second button.

Costing only works if the three steps above are honest

Planned versus actual cost per build falls out of NetSuite automatically once BOM, routing and completions are reliable. There is no separate costing project. The SuiteAnalytics dashboards and the Power BI views over ODBC were the smallest part of the work, and they went live last because they would only have shown how wrong the inputs were.

Month-end production reconciliation disappeared, not because of a reconciliation tool, but because production and inventory were finally the same transactions in the same system.

What I would do again

  • Clean the BOMs with the people who build the product, before anything is loaded. They know which quantities are fiction.
  • Pick the material issue moment to match the floor, and automate it so nobody has to remember.
  • Make completion entry a thirty-second job. Everything downstream depends on it being done at the time.
  • Hold the dashboards back until two weeks of real builds have gone through. The first dashboard a plant manager sees should be one they can trust.

Standard NetSuite covered nearly all of it. The scripts were small and sat at the moments where a person would otherwise have had to remember a step. That balance, standard where it fits and code only at the seams, is the one I now aim for on every module rollout.
